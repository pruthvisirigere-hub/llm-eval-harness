# llm-eval-harness

A small LLM evaluation + observability harness. It answers a fixed set of
questions, scores the answers, and tells you where your system is weakest —
with latency, tokens, and cost tracked next to every score.

Built to be the honest counterpart to a RAG project: if CodeRAG answers
questions, this harness proves whether those answers are any good.

## What it does

1. Loads a knowledge base (`data/kb.md`, a fictional coffee company) and an
   eval set of 20 questions (`data/eval_set.jsonl`, 5 categories).
2. Answers each question with a **model**:
   - `local` (default): TF-IDF retrieval over the KB, extractive answers.
     No API key, no downloads beyond `pip install`.
   - `openrouter`: an OpenRouter chat model with the KB as context, for
     comparing a real LLM against the local baseline.
3. Scores each answer by keyword match against the expected facts.
4. Aggregates overall + per-category accuracy, latency, tokens, cost.
5. Writes `results/report.json`, `results/report.md`, and
   `results/traces.jsonl` (one JSON line per question).

## How to run

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

python run_eval.py               # local model, no API key needed
```

Compare against a real LLM (needs an OpenRouter key):

```bash
export OPENROUTER_API_KEY=sk-or-...
python run_eval.py --model openrouter
```

Useful flags: `--dataset`, `--kb`, `--config`, `--output-dir`.

## How to read the report

`results/report.md` has three parts:

- **Headline metrics** — accuracy, mean score, avg latency, total tokens and
  estimated cost.
- **Per-category accuracy** — the important table. A good overall score can
  hide a bad category.
- **Findings** — names the weakest category, lists the failed questions and
  which keywords they missed, and calls out the slowest question.

`results/report.json` has the same numbers in machine-readable form, so you
can compare runs over time. `results/traces.jsonl` has one line per question
with the question, the full answer, the score, latency, tokens, and cost —
that is the observability trail.

## Example report (real run, local model)

From the verified run in this repo — 20 questions, 19 passed:

```markdown
# Eval Report

- **Questions:** 20
- **Passed:** 19 / 20
- **Accuracy:** 95.0%
- **Mean keyword score:** 0.93
- **Avg latency:** 0.00s per question
- **Total tokens:** 199 in / 1341 out
- **Total estimated cost:** 0.8345 USD
- **Pass threshold:** score >= 0.5

## Per-category accuracy

| Category | Questions | Passed | Accuracy | Mean score |
|----------|----------:|-------:|---------:|-----------:|
| brewing  | 4 | 4 | 100.0% | 1.00 |
| company  | 4 | 4 | 100.0% | 1.00 |
| policies | 4 | 4 | 100.0% | 1.00 |
| pricing  | 4 | 3 | 75.0%  | 0.75 |
| products | 4 | 4 | 100.0% | 0.88 |

## Findings

- **Weakest category: pricing** — 3/4 passed (75%, mean score 0.75).
- **1 question(s) failed:** "How much do you need to spend for free
  shipping?" (score 0.00; missing keywords: $35, free shipping) — the
  retriever picked the wrong KB chunk, and the KB never says "free
  shipping" in those words. That is exactly what an eval is for: it found
  a real gap instead of a vibes-based "looks fine".
```

Note the honest details: the "cost" for the local model is what the same
traffic *would* cost at API prices (the local model itself is free), and
token counts are estimated as `characters / 4`. See `STUDY.md` for why those
caveats matter and what a good eval set looks like.

## Tests

```bash
pytest
```

8 tests: scoring (all / none / partial keywords), per-category aggregation,
cost math, token estimation, empty-dataset handling, and a full end-to-end
run that checks all three report files are created with real numbers.

## Project structure

```text
llm-eval-harness/
├── run_eval.py            # the harness: load, answer, score, report
├── config.yaml            # pass threshold, prices, OpenRouter settings
├── requirements.txt       # scikit-learn, pyyaml, pytest
├── data/
│   ├── kb.md              # fictional knowledge base (Blue Peak Coffee)
│   └── eval_set.jsonl     # 20 questions, 5 categories, expected keywords
├── tests/
│   └── test_harness.py    # 8 pytest tests
├── results/               # generated by each run (gitignored)
│   ├── report.json
│   ├── report.md
│   └── traces.jsonl
├── README.md
└── STUDY.md               # picture-first explainer + interview questions
```

## Extending it

- Grow the eval set from 20 to 50+ questions and add unanswerable ones (the
  system should say "I don't know", not invent an answer).
- Add a third model: point the harness at a RAG system's `/api/ask/`
  endpoint and compare it against local + OpenRouter on the same questions.
- Add retrieval metrics (was the right KB chunk retrieved?) next to answer
  metrics, and an LLM-as-judge scorer alongside keyword match.
